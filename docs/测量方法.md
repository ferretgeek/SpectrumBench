# 测量方法 / Measurement Method

## 核心原则

SpectrumBench 测的是单个连续工作流，不是并发吞吐。三种模式的提示词、预热数、最大输出、推理等级范围和缓存策略都由代码锁定；界面不会开放会破坏可比性的自定义并发或提示词。

1. 每轮使用 Responses API 流式输出，并记录请求开始、首个可见文本事件、最后一个可见文本事件与请求结束时间。
2. 只在响应提供完整 `usage` 时计入精确 Token 与 API 等效成本；中断请求的估算单列。
3. 可见输出 Token = 输出 Token − 推理 Token。
4. 可见速度 = 首个可见文本块之后的可见 Token ÷ 首尾可见文本事件间隔。
5. 端到端可见速度 = 全部可见 Token ÷ 请求开始到最后可见文本事件的间隔。
6. 预热会计入 usage 与缓存观察，但不进入正式速度分布。
7. 主速度结论使用正式样本中位数；样本不足、波动过高或 usage 明细不完整时，质量门禁会降级结论。

美元数值只是 `pricing_table.json` 的静态 API 等效换算。服务层级不是 `default`、要求的缓存写入明细缺失、上下文超过表内边界或模型未知时，不发布误导性的成本结论。

## Three locked modes

- **Uncached limit** places a same-length randomized marker at the front of each prompt to defeat prefix caching and measure a deliberately expensive boundary.
- **Daily conversation** grows a six-turn pair-programming conversation with mixed questions, fixes, tests, and review work.
- **High-cache Codex** reuses a long, stable code context and cache key with high/xhigh reasoning to observe a cache-friendly workflow.

All modes are single-stream and serial. Complete usage is authoritative, interrupted estimates stay separate, warm-ups are excluded from the formal distribution, and the median is the primary speed statistic.

## 解释边界 / Interpretation boundaries

- 网络路径、服务负载、账号等级、区域和时间都会影响结果；一次运行不能代表所有环境。
- 不同模型、模式版本、推理等级或质量状态的速度倍率不会被当作直接可比。
- “额度耗尽”只有在上游明确返回相应终止信号时才成立；手动停止不等于已测出额度上限。
- Preview 和 Demo 使用无网络的展示状态，不是实际模型成绩。
